## 一、代码仓储与同步（底层基础设施）

### 1.1 Git 仓库管理

| 维度 | 内容 |
|:-----|:------|
| **现状** | 单仓库 ~1GB（含 .git 409MB + 工作树 594MB），包含浏览器缓存 `.so` 文件 |
| **问题** | push 超时、clone 慢、冲突频繁、新机器部署痛苦 |
| **目标** | 纯代码仓库 ≤50MB，运行时数据不入库 |
| **方案** | ① 更新 .gitignore ② git filter-branch 清除历史大文件 ③ 配置 git-lfs 管理大文件 |
| **难度** | ⭐⭐（git filter-branch 需谨慎操作，建议先备份） |
| **影响** | 📐 跨机 — 所有机器 clone/push 速度提升 10x |
| **🔗 连锁** | → 路径统一(1.3) → 依赖管理(1.4) 前置条件 |

### 1.2 多机同步机制

| 维度 | 内容 |
|:-----|:------|
| **现状** | WPRA 写分区·读聚合 v2.0。每台机器写 machines/{uid}/，Dashboard 聚合读取。但 guardd 仍有全局写入 |
| **问题** | `_registry.json` 历史冲突、`git add -A` 跨文件 staging、架构复杂 |
| **目标** | 废除 WPRA 写入端，改为 ORACLE 只读 + heartbeat 仅汇报 |
| **方案** | ① 创建 ORACLE.yaml（只读宪法）② 每台机器读 ORACLE 对账 ③ heartbeat 精简为仅状态汇报 ④ 删除 WPRA 写入代码 |
| **难度** | ⭐⭐⭐（涉及 guardd、Dashboard、matrix_mgmt 多个模块修改） |
| **影响** | 📐 系统 — 消除 Git 冲突根源，简化整体架构 |
| **🔗 连锁** | → 影响所有涉及多机数据同步的模块 |

### 1.3 路径统一

| 维度 | 内容 |
|:-----|:------|
| **现状** | 12+ 处 `Path.home() / "workbuddy-agent-os"` 硬编码在 app.py，其他文件更多 |
| **问题** | 每台机器 home 目录/结构不同，改一台其他都断 |
| **目标** | 所有代码使用 `$AGENT_SYNC` / `$AGENT_LOCAL` 环境变量 |
| **方案** | ① 在 .zshrc 定义环境变量 ② 批量替换所有脚本中的硬编码路径 ③ Dashboard base.py 已经定义了常量，推广使用 |
| **难度** | ⭐（机械替换，但需全面扫描所有文件） |
| **影响** | 📐 跨机 — 解决 80% 的跨机兼容性问题 |
| **🔗 连锁** | → 是其他所有优化的前置条件 |

### 1.4 依赖与环境管理

| 维度 | 内容 |
|:-----|:------|
| **现状** | Python 3.9(系统) + 3.13(管理) 并存，orjson 签名问题，Camoufox 依赖复杂 |
| **问题** | 新机器部署步骤多，环境不一致导致同一代码表现不同 |
| **目标** | 一键检测+安装+修复环境 |
| **方案** | 升级 init.sh：检测 Python/Node/依赖/签名问题，自动修复或报清晰错误 |
| **难度** | ⭐⭐（编写检测逻辑，测试各机器） |
| **影响** | 📐 局部 — 降低新机器部署时间从 2 小时到 10 分钟 |
| **🔗 连锁** | → 依赖 1.1(仓库干净) 和 1.3(路径统一) |

## 二、账号管理体系

### 2.1 账号注册与配置（accounts.yaml）

| 维度 | 内容 |
|:-----|:------|
| **现状** | 本地 `agent-local/tools/matrix/config/accounts.yaml` 定义账号，WPRA 有一份拷贝 |
| **问题** | 两份数据不一致时互相覆盖，同步逻辑复杂 |
| **目标** | 单一权威来源，本地配置规范化 |
| **方案** | 废除 WPRA 的 accounts.yaml，只用本地一份。ORACLE.yaml 只定义"哪个机器有哪些身份" |
| **难度** | ⭐⭐（需修改 matrix_mgmt.py 的读取逻辑） |
| **影响** | 📐 模块 — 消除账号数据的不一致性 |
| **🔗 连锁** | → 依赖 1.2(同步机制) |

### 2.2 身份管理（Identity）

| 维度 | 内容 |
|:-----|:------|
| **现状** | 身份按手机号聚合，一个身份可绑定多平台。已在 Dashboard 实现删除/解绑功能 |
| **问题** | 基本功能已有，但身份目录命名不一致（有的 `phone_xxx` 有的直接用账号名） |
| **目标** | 统一身份命名规范，梳理现有身份的目录结构 |
| **方案** | 将独立身份目录（douyin_133 等）统一命名为 phone_xxx，清理 xhs_01 等遗留目录 |
| **难度** | ⭐（主要是数据迁移工作，系统逻辑已支持） |
| **影响** | 📐 局部 — Dashboard 身份管理页更清晰 |
| **🔗 连锁** | → 依赖 2.1(账号配置) |

### 2.3 登录态管理

| 维度 | 内容 |
|:-----|:------|
| **现状** | Cookie 存储在 `identities/{name}/user_data/cookies.sqlite`，可通过 `mc login` 扫码登录 |
| **问题** | Cookie 过期后系统不一定能及时发现，需人工检查 |
| **目标** | 自动检测 Cookie 有效性 + 登录态过期告警 |
| **方案** | 在 guardd 或定时任务中加入 Cookie 有效性检查，过期时 Dashboard 标红 |
| **难度** | ⭐⭐（需要实现 Cookie 有效性验证逻辑） |
| **影响** | 📐 局部 — 减少"以为登录了其实过期了"的情况 |
| **🔗 连锁** | → 依赖 1.4(环境) 和 2.1(账号) |

## 十、综合评估

| 维度 | 评估 |
|:-----|:------|
| **总工作量** | 阶段1: 2-3天 | 阶段2: 3-5天 | 阶段3: 按需 |
| **最大痛点** | Git 仓库 1GB + 路径硬编码（阶段1解决） |
| **最大风险** | guardd 重构（6.2）和同步机制变更（1.2）涉及面广 |
| **最小投入最大收益** | 路径统一(1.3) + Git 减肥(1.1) — 两天解决 80% 痛苦 |
| **是否可分批推进** | ✅ 三个阶段完全独立，阶段1做完即可显著改善体验 |
