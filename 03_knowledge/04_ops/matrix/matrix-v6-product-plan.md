## 三、模块详细设计

### 3.1 短信验证码模块（P0）

**目标**: 自动接收短信验证码，完成账号登录/恢复/验证

**现有基础**: `03_knowledge/40_references/matrix-sms-verification.md` 已有 API 方案

```
养号脚本需要验证码
  ↓
ApiSMSHandler.wait() 启动轮询
  ↓ 每3秒拉一次API (wx.tyhtak.com / 其他供应商)
检测到新短信 → 提取验证码（4-6位数字）
  ↓
返回给登录流程自动填入
  ↓
登录完成后标记验证码已使用
```

**设计要点**:
- 抽象 `SMSHandler` 基类（已存在 `matrix_modules/account/sms/base.py`）
- 支持多供应商切换（tyhtak / 其他API / 自建短信猫）
- 手机号关联账号配置（`accounts.override.yaml` 中的 phone 字段）
- 超时 120 秒，失败告警
- 验证码消耗后标记，避免重复使用

**配置示例**:
```yaml
# config/sms.yaml
sms:
  provider: tyhtak
  api_key: "gtmsg2026"
  poll_interval: 3
  timeout: 120
```

**目标**: 生成真实、多样、上下文相关的评论内容

**现有基础**: `scripts/config/comment_corpus.yaml` 已有基础语料

**架构**:

│  │ (预设模板)  │  │ (本地LLM)  │  │  (已发评论/已评视频) │   │
│  └─────┬──────┘  └─────┬──────┘  └──────────┬───────────┘   │
│        │               │                    │               │

│                ▼                ▼                           │
│         ┌────────────┐  ┌────────────┐                      │

**语料分层**:

| 层级 | 来源 | 用途 | 特点 |
|------|------|------|------|
| L1 静态模板 | 人工预设 | 日常普通评论 | "学到了"、"真不错"、"支持" |
| L2 关键词模板 | 按视频类型匹配 | 相关评论 | 科技→"技术流"、美食→"看着就好吃" |
| L3 AI 生成 | 本地 oMLX + Qwen | 精准评论 | 根据视频标题/描述生成 |
| L4 上下文延续 | 追评/回复 | 互动 | 基于已有评论内容 |

**存储**:

    - text: "好实用呀"

### 3.3 定向评论任务系统（P0）

**目标**: 接收指定 URL，让所有账号去该视频下评论，时间错开、内容不同

**工作流程**:

```
用户/智能体下发任务:
  "给这些视频发评论: [url1, url2, url3]"
    ↓
任务中心解析 →
  提取视频ID → 分析视频内容/标题 → 确定评论策略
    ↓
生成评论计划 →
  每个账号 → 分配不同的评论内容 → 设置时间偏移
    ↓
任务写入 cross_machine/tasks/ →
  持久化到 cross_machine/data/matrix/comment_tasks/
    ↓
各机器 guardd 检测到新任务 →
  按计划执行评论（时间错开 5-30 分钟）
    ↓
完成后上报结果 →
  cross_machine/data/matrix/comment_results/{uid}.json
```

**任务格式**:
```json
{
  "task_id": "comment_20260612_001",
  "url": "https://www.douyin.com/video/xxx",
  "platform": "douyin",
  "type": "batch_comment",
  "strategy": "diverse",
  "accounts": ["douyin_01", "douyin_02"],
  "time_window": {"start": "10:00", "end": "12:00"},
  "min_interval": 300,
  "assigned": {
    "douyin_01": {"text": "讲得真好，学到了", "time": "10:05"},
    "douyin_02": {"text": "这个角度很新颖", "time": "10:12"}
  },
  "context": {"video_title": "xxx", "author": "yyy"},
  "status": "pending"
}
```

### 3.4 评论互动系统（P1）

**目标**: 追评、回复作者回复、与其他用户互动

**场景**:
1. 发布评论后 → 如果作者回复了 → 自动追评回复
2. 其他用户回复了我们的评论 → 选择性回复

**技术方案**:
- 评论发布后记录 `{comment_id, video_id, account}`
- 定时检查是否有新回复（通过评论区 DOM 或 API）
- 检测到回复 → 加载回复内容 → 确定回复策略 → 回复

**频率控制**:
- 每天最多回复 5 条/账号
- 回复间隔至少 30 分钟
- 回复内容需与原文相关

### 3.5 账号健康度与反检测（贯穿全局）

**风险维度**:

| 风险 | 检测方式 | 应对措施 |
|------|---------|---------|
| 操作频率过高 | 各操作 rate limit | 按分钟/小时/天三级限速 |
| 行为模式单一 | 蓝图随机化 + wait_jitter | 操作间隔随机化 |
| 内容重复 | 语料库去重 | 同一内容不重复使用 |
| 登录地点异常 | IP 检测 | 静态住宅 IP / 代理 |
| 设备指纹一致 | BrowserForge | 每账号独立指纹 |
| 评论时间集中 | 时间策略 | 错开 5-30 分钟 |
| 评论内容异常 | AI 质量检测 | 敏感词过滤 + 长度变化 |

**账号健康度评分**:
```python
class AccountHealth:
    def score(self, account_id) -> dict:
        return {
            "overall": 85,          # 0-100
            "risk_level": "low",    # low/medium/high
            "metrics": {
                "daily_ops": 45,    # 今日操作数
                "op_freq": 0.8,     # 操作频率 vs 安全阈值
                "comment_rate": 0.3, # 评论占比
                "repeat_rate": 0.05, # 内容重复率
                "fail_rate": 0.1,   # 操作失败率
                "days_active": 15,  # 连续活跃天数
            },
            "alerts": []            # 预警列表
        }
```

### 3.7 定时策略引擎

**核心规则**:
- 养号时间分布：分散在 8:00-22:00，每次 15-30 分钟
- 评论间隔：同一视频不同账号间隔 5-30 分钟
- 跨视频间隔：同一账号不同视频间隔 10-60 分钟
- 账号休息日：每周 1-2 天静默

**策略配置**:
```yaml
strategy:
  daily:
    time_windows: ["09:00-09:30", "14:00-14:30", "20:00-20:30"]
    round_per_window: 2
    interval_between_rounds: 45-90
  comment:
    min_interval: 300        # 同账号评论最短间隔（秒）
    max_daily: 10            # 单账号每天最多评论
    batch_spread: 1800       # 同一批任务最大散布时间（秒）
  rest_day:
    probability: 0.15        # 每天有 15% 概率静默
```

## 七、关键设计原则

### 7.1 反检测第一

所有操作设计优先考虑反检测：

1. **频率控制**: 每个操作独立 rate limit（like/comment/search/follow）
2. **时间随机化**: 所有等待时间加 jitter ±30%
3. **内容去重**: 同一内容不在 7 天内重复
4. **IP 分散**: 多账号用不同代理出口
5. **行为多样性**: 每次养号随机选择蓝图组合
6. **账号休息**: 模拟真人作息（夜间不操作）

### 7.2 联邦优先

1. 每台机器独立执行本地任务
2. 任务通过 cross_machine 文件异步传递
3. 机器间不直接通信（避免网络暴露）
4. 任务结果通过 Git 被动同步
5. Dashboard 统一展示联邦状态

### 7.3 渐进增强

1. 现有功能不动（养号引擎稳定）
2. 新功能先以独立模块开发
3. 通过 mc CLI 子命令暴露新功能
4. 每完成一个模块就做回归测试
5. 保持向后兼容

## 八、风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 平台接口变更 | 选择器失效 | 多级选择器 fallback + 定期验证 |
| 封号 | 账号损失 | 健康度预警 + 操作上限 + 新号先养 |
| 浏览器检测 | 所有账号受影响 | Camoufox 指纹隔离 + BrowserForge |
| 短信API不可用 | 无法登录 | 多供应商切换 + 手动兜底 |
| 代理不稳定 | 操作失败 | 自动切换代理 + 超时重试 |
| 跨机冲突 | 同一任务重复执行 | 任务状态机 + TTL |
